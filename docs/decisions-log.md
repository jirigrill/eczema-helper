# Decisions log

Settled, implemented decisions that are worth recording but not worth a full ADR. Each line is the decision as it stands today; the fuller reasoning (and any rejected alternatives) lives in git history under the original ADR file noted in parentheses. This is also the go-forward home for ordinary settled decisions — reserve a numbered ADR in `docs/adr/` for calls that constrain not-yet-built work or would need a deliberate revision to reverse.

- **Meals are day-granular, one per slot per actor.** `Meal` is keyed by `date` + `mealType` + `actor` (composite `MealId` `"${date}:${mealType}:${actor}"`), so a `(date, mealType)` pair holds up to one meal per actor; there are no user-facing meal times, and `createdAt` / `updatedAt` are system-stamped for audit. Breastmilk allergen transit is too diffuse for hour precision, and the rest of the model is already day-keyed. The `actor` dimension is the dual-actor build (ADR-0027, parked with the protocol engine — see [parked features](parked-features.md)). *(was ADR-0003)*
- **In-memory port adapters were dropped.** The hand-written `InMemory*` fakes for `ScheduleRepository` / `QuestionnaireRepository` had no consumers and were removed; adapters are tested against `fake-indexeddb`. *(was ADR-0013)*
- **Meal logging is commit-gated with fixed-at-entry type.** The `/meal` flow builds a working meal in memory and persists it only on the `Uložit` commit; the meal type is chosen at entry and not mutable mid-edit (no move/switch pills); deleting a whole meal is an explicit destructive-confirm action. *(was ADR-0018)*
- **Food-source subgroup is a second presentation axis.** A family's foods can cluster under a curated `familySources` subgroup (e.g. Kravské / Ovčí / Kozí / Rostlinné, S lepkem / Bez lepku) above the allergen axis — applied only to families with ≥ 5 foods and an authored entry, unsourced foods falling into a trailing *Ostatní*. Source is presentation-only and never enters the trigger path; the former `bez alergenu` grouping was dropped because it read as a false safety claim. *(was ADR-0019)*
- **Unlogged meal-slot rows are tappable add-entry points.** In `MealCard`, an unlogged slot row is a link that opens `/meal` with that slot's meal type pre-selected — a deliberate exception to the otherwise FAB-only write path. *(was ADR-0020)*
- **oxlint stays out for now.** Evaluated as a fast pre-filter ahead of ESLint (#480); as of oxlint 1.74.0 it has no Svelte plugin, so it can't lint the ~45 `.svelte` files that make up a fifth of this repo's lintable surface, and `bun run lint` already completes in ~4s. Revisit once oxlint ships Svelte support.
- **The loggable-window guard exempts unchanged-date edits.** `DexieMealRepository.save()` / `DexieSkinObservationRepository.update()` now compare the payload's `date` against the already-stored row's `date` (via `checkLoggableWindow`'s optional `existingDate` param) and skip the window check when they match, so editing a row that's already outside the window (e.g. after a schedule regeneration) doesn't block on fields that never touched the date. Explicit date changes are still guarded either way. The `/meal` and `/skin` editors show a passive "outside the protocol window" hint on such rows. *(#440)*
- **The ladder engine exposes a pure trace seam, not a parallel re-derivation.** `decideLadderMove` and `explainLadderMove` both delegate to one internal `walkLadderPrecedence`; the explain surface (`LadderExplain` = `{ decision, snapshot, steps }`, with `LadderStateSnapshot` projecting five replay facts and `steps` a fixed 6-tuple in precedence order) is an additive, read-only exposure of behavior the precedence already runs, so trace and verdict cannot drift. `deriveLadderState`/`LadderReplayState` stay private; `tools/ladder-viz` reads the cadence/skin-stability signals off this seam instead of re-calling the gates. *(#528, design #521)*
- **Ladder-viz scenarios are YAML, Zod-validated on load, with strict dates.** `tools/ladder-viz/scenarios/*.yaml` (header `allergen`/`phase`/`stage`/`permanent?` + `days: [{date, events}]`, event kinds `meal`/`skin`/`eval`) parse into the shared `JourneyRun` event-stream type both the replay and (future) manual mode render. Dates must be strict, consecutive, ascending — a duplicate / out-of-order / skipped date is a loud load error, since time-triggered engine transitions only render when every calendar day is a real entry. The allergen is validated against the catalog at the load boundary; the ladder is resolved from that catalog entry. *(#532, format settled in #523)*
- **The ladder explain seam carries a per-event replay trace for the viz tool.** `LadderExplain` gained a `replay` field (`LadderReplay` = `{ initial, steps }`, one `LadderReplayStep` per replayed `deriveLadderState` event, each with the branch taken + before/after frame). Produced by instrumenting the real loop via an optional sink — no parallel replay, no logic in the viz tool (the domain classifies the branch; the adapter only labels it). Derived and non-load-bearing (ADR-0012): no decision path reads `replay`. `tools/ladder-viz` renders it as a "replay ledger" under the pipeline, with pipeline back-links into the event that set the ceiling / pending reaction. Guarded by a "last step after == snapshot" test; maintenance contract lives on the `LadderReplayStep` type. A follow-up (#550) may unify the `LadderPrecedence*` / `LadderReplay*` naming under a `...Trace` family. *(builds on #528, design #521)*
- **FeedingStage is a live master switch, not a hardcoded constant.** A dedicated `settings` Dexie singleton (`SettingsData.feedingStage`, `SettingsRepository` port + adapter + `settingsContext` reactive store) holds the stage, seeded at first run and changeable via a Settings segmented control (`settingsStore.setFeedingStage`, owned by `stores/settings.svelte.ts`). It gates the actor pills via `getEligibleActors` and, since the descaling (PRD #623), is also the app's *seeded* signal. *(#567, parent spec #564; revised ADR-0023 §Feeding stage — ADR-0023 parked with the protocol engine, see [parked features](parked-features.md))*
- **Emptying a meal deletes it.** `MealEditor.finalize()` on an *existing* meal with zero confirmed foods removes the persisted row and reports `'deleted'`; on a compose-new it stays a no-op. Removing every food and then saving or backing out is a legitimate delete path — equivalent to the explicit "Smazat jídlo", writing the same `meal-delete` discard buffer so the `Jídlo smazáno` toast + `Zpět` undo behave identically. The edit CTA stays enabled when emptied (an inline hint warns that saving deletes the meal); `swapActor`'s silent autosave deletes an emptied departing meal too. Reverses the earlier #586 rule that "an empty meal never persists / empty-save is a silent no-op routing to Smazat". *(#588)*
- **Copy a meal to another slot.** The `⋯` overflow on the meal editor exposes *Kopírovat jídlo* (only when the source meal has ≥1 food) → a destination picker (reused `DayStrip` + `FabActionSheet` slot sheet). The copy is **same-actor** (no actor picker; the destination is resolved actor-scoped via `loadBySlot(destDate, destSlot, source.actor)`) and **eligibility is not re-checked** on the destination date. Since the descaling (PRD #623 §3e) every reachable picker cell is a legal destination — the strip spans `earliest logged … today`, so no cell is future or out of window, and the "Kopírovat sem" button is always enabled. The merge is **additive, dedup-by-`foodId`, destination-wins** (a collision keeps the destination item, differing portion/prep does not override), the **source note never travels**, timestamps mirror ADR-0018, and a copy that would add nothing is a **no-op**. The write is **silent-merge with undo** (a `meal-copy` discard descriptor reverses just the added items / created row, invalidated by any manual edit of the destination). No new ADR — the merge lives in the pure `copyMealInto` assembler and the flow reuses existing components. *(spec #599)*
- **Restartovat is a true factory reset, behind a confirm.** `resetDatabase()` (`src/lib/db/reset-database.ts`) clears **every** table via `db.tables`, not a hand-written list. The predecessor (`settingsStore.reset()`) named four tables — three of them empty after the descaling — and spared the five holding the mother's meals, skin observations and photos, while the Czech copy promised to erase all saved data. The wipe is now honest, the copy names the photos, and a `ConfirmSheet` guards it: the action is irreversible and no backup mechanism exists, so the device holds the only copy. A whole-database wipe belongs to no domain, so it sits beside `atopic-db.ts` and outside per-domain adapter ownership. *(review of PR #638)*
- **One adapter instance per domain, owned by that domain's session store.** `stores/meal-session.ts` exports `mealRepository`; `stores/skin-observation-session.ts` exports `skinObservationRepository`. Four sites previously hand-rolled `new DexieMealRepository(db)`, leaving no single seam for the storage swap the architecture exists to enable. Cross-domain readers (`stores/earliest-logged.ts`) import the owning stores' instances rather than constructing their own. Module-scope singletons, not a DI container: adapters are tested against `fake-indexeddb`, so constructor injection would be ceremony with no payoff. *(review of PR #638)*
- **The day strip reaches back to the earliest logged day and a fixed week into the future, with no hard limit.** `computeDayStrip` spans `min(today − 7d, earliestLogged, selectedDate) … max(today + 7d, selectedDate)`. A ±7-day window around today is always present as a floor; logged data only ever extends the *past* edge outward. The future edge is fixed at today + 7d — future-dated entries never push it further (so no `latestLogged` boundary is needed). Fresh install → a symmetric 15-cell window. Future days are ordinary, fully-loggable days — `resolveDay` no longer redirects a future param to today, and direct URL nav to a date outside the span still clamps the range outward to render it. No hard cap on past span (single-user PWA; contiguous render, no virtualization). No ADR — no not-yet-built work is constrained. *(#654)*
- **No crypto in the tree; the app has no backup and no encryption at rest.** `src/lib/crypto/` (AES-256-GCM + PBKDF2 over Web Crypto) was deleted. It had been written up front against the former ADR-0002 "encrypted manual export is the v1 backup floor" and then sat unwired since the Phase 0 scaffold — no module in `src/` ever imported it, so its only caller was its own test file. Both prospective consumers are now gone: photo encryption-at-rest (#467) was closed `wontfix` as deprioritized, and the export payload builder (#438) is closed with this change. Keeping dead crypto invited the assumption that something was protected when nothing was. Consequences accepted, and they compound: the device holds the only copy of a multi-month medical journal, so hardware loss or the Settings factory reset destroys it outright; photos and every other record sit plaintext in IndexedDB, which is why the app stays on the developer's own device. Reviving either capability starts by restoring this module from git history (last present at `706bec7`) — the primitives were sound but the one-shot `encrypt(data, passphrase)` shape re-derives the key per call, so at-rest use needs a cached-`CryptoKey` variant, not a straight restore. *(closes #438; #467 closed separately)*
